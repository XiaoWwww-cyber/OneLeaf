# RAG 架构演进实施方案

为了彻底解决知识库检索在“长文本召回极慢”、“宽泛问题无法准确定位”、“不同跨越时间/文档信息难以聚合”以及“大模型上下文幻觉”等痛点，依据业界最佳实践，我们将按照以下 5 个维度的演进路线对核心检索机制进行彻底改造。

以下方案按落地性价比与实施顺序排列：

## 1. 核心基石：结构化与精细化文档切片 (Structural Chunking) —— [最高优先级，即刻执行]

目前系统将完整文件作为一个巨大向量存入数据库，这是导致大文件干扰和上下文爆缸的根本原因。单纯按字数一切到底也容易切碎原有的逻辑段落。

### 改造方案

- **一阶结构切片 (Semantic/Structural Chunking)**：
  - 优先按照 Markdown 标题（`#`, `##` 等）或段落双换行符（`\n\n`）进行逻辑分块。保证一个 Chunk 尽可能包含一个完整的语义段落。
- **二阶滑动窗口兜底 (Sliding Window)**：
  - 如果某个结构化段落依然超过了安全界限（例如 `800` 字符），则在此块内部使用滑动窗口（例如限制在 `500` 字左右，保留 `50-100` 字的 Overlap）进行强切。
- **数据结构解耦 (`vector_db.rs` / `knowledge_base.rs`)**：
  - `documents` 表保持原样，仅存储文件元数据与完整原始文本。
  - `document_vectors` 表重构：引入 `chunk_index` 和 `chunk_content`。一个 Document 将对应多个 Vector Chunks。

## 2. 上下文组装：元数据溯源 (Metadata Traceability) —— [高优先级，伴随第一步]

发送纯文本片段给大模型容易导致信息混淆和幻觉，大模型无法得知这些片段来自何时何地。

### 改造方案

- **强注入物理出处**：
  - 在最终拼入发给 LLM 的 `context_prompt` 时，必须为每个 Chunk 强行注入其来源信息。
  - 格式示例：
    ```
    【参考片段 1】(来源文件: 2025年11月总结.md | 分类: documents)
    内容: [Chunk 内容]...
    ```
  - 这能赋予大模型“引用来源”的能力，让其回答：“根据 11 月的总结显示...”。

## 3. 混合检索与 RRF 融合 (Hybrid Search) —— [高优先级]

单纯依赖向量检索对强依赖特定专有名词、名称代号的查询极度不敏感。

### 改造方案

- **双路并发召回 (Concurrent Hybrid Search)**：
  - 在 `chat_with_ai` 时，利用 `tokio::join!` 异步**并发执行** Tantivy（全文搜索关键字）与 OnnxEmbedder（语义向量搜索），减少阻塞时间。
- **RRF (Reciprocal Rank Fusion)**：
  - 在 Rust 端编写合并打分算法：`Score = 1 / (K + rank_vector) + 1 / (K + rank_tantivy)` （通常 K 取 60）。
  - 这完美弥补了向量搜索对特定专有名词忽视的缺陷。

## 4. 两阶段检索：粗排召回 + 交叉精排 (Reranking) —— [中短期升级]

彻底解决“虚假高匹配”（如完全不跨界的文档碰巧被相近词组带高得分）。由于 ONNX 是 CPU 推理密集型，必须严格控制线程阻塞。

### 改造方案

- **第一阶段 (低成本广撒网)**：双路召回（Hybrid Search）请求扩宽 `limit`（例如 30），设置极低阈值（如 `0.2`），初筛提取这 30 个 Chunks。
- **第二阶段 (高精度并发交叉打分)**：
  - 加载 `bge-reranker-v2-m3` ONNX 模型。
  - **异步性能保障**：**严禁** 在主异步任务里直接 run ONNX。必须使用专门的计算线程池 `tokio::task::spawn_blocking` 来包裹 ONNX Reranker 推理逻辑，防止重排 30 个 Chunks 时 Tauri 前端 UI 渲染和通信出现严重卡顿假死。
  - 获取极其精准的特征级交叉相似度后，筛选 Top 3-5 送给 LLM。

## 5. 查询重写 (Query Transformation) 与 元数据前置过滤 —— [长远规划]

解决口语化短文本没特征，以及跨服海量历史查询效率低下的痛点。

### 改造方案

- **智能重写**：前置拦截用户短对话（比如：“怎么弄这个？”），调用极快的小模型将其“扩写”为高密度的搜索词。
- **智能路由与前置过滤**：识别出隐含的时间条件（“去年一整年”），在 SQL 查询向量层面支持传入 WHERE 过滤条件（如 `year=2025`），物理截断无关年份干扰。
