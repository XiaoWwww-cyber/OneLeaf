# OneLeaf 智能记忆管理引擎 (分层长时记忆) 演进实施方案

在吸收业界先进的记忆架构（如 Spring AI / LangChain Memory）与我们现有的“大模型多路聚合搜索平台 (RAG)”的基础之上，针对 OneLeaf 桌面端的特定技术栈（Rust + Tauri + SQLite + Tantivy）与双引擎架构（本地 LM Studio / 联机大模型 API）痛点，特制订此**分层长时记忆（Hierarchical Memory）**优化方案。

---

## 方案可行性分析与现状盘点

本方案**极其契合**当前项目的底层设计，可行性极高：

1. **物理层已就绪：** 我们在 `vector_db.rs` 中已经建立了 `conversations`、`messages`、`message_vectors` 等表，且带有向量维度记录，这意味着第四层（长期记忆 RAG）的数据管道已经跑通了一半。
2. **模型解耦层已就绪：** `ai.rs` 和前端都已经做完了针对不同 Provider（豆包、OpenAI、DeepSeek、LM Studio）的抽象，在此之上做调度分发是水到渠成的。
3. **亟待解决的痛点：**
   - 当前在 `commands/ai.rs` 中的上下文组装策略，仍停留在粗放地往 System Prompt 头部拼接历史结果（且仅仅做了 RAG 的拼接），并没有对单轮会话中的长对话进行精细的 Token 及逻辑管理。
   - 现有的“短期窗口”没做强制限制，“中期摘要”完全缺失，也没有独立的用户级“长期画像”。

为此，我们需要严格执行下述的**四层模型**和**双引擎调度**。

---

## 一、 核心架构设计：四层记忆模型

我们在现有的 RAG 架构基础上，为“聊天会话”引入独立的四层生命周期管理：

### 第一层：用户画像 (User Profile) - 绝对置顶

- **内容**：提炼自用户的核心身份、偏好、长期指令（如：“我叫张三”、“不要用Markdown表格回答”、“倾向于简洁的代码片段”）。
- **机制**：由大模型异步常驻提取，以 JSON 形式固化至 SQLite 全局表 `user_profiles`，无条件注入每一次对话的 System Prompt 极高优先级位置。

### 第二层：短期记忆 (Short-term) - 滑动窗口

- **内容**：当前会话中，最近的 4 到 6 轮完整对话记录（确保上下文语境绝对精确，保持高保真的近况上下文交互）。
- **机制**：直接从 SQLite `messages` 表中 `ORDER BY created_at DESC LIMIT 6` 捞取，不需额外处理。

### 第三层：中期摘要 (Mid-term Summary) - 滚动压缩

- **内容**：单会话过长（超过 10 轮）时，将前些轮次的细节压缩为一段 200 字以内的摘要（例如：“用户正在探讨RAG系统的切片方案，并排除了按字数硬切的做法”）。
- **机制**：由后台服务触发大模型进行总结，存储在 `conversations` 的字段中，随会话持续向前推进、覆盖更新。极大程度上节省长对话的 Token 消耗与幻觉累积。

### 第四层：长期记忆 (Long-term RAG) - 向量寻回

- **内容**：跨越时空的所有历史对话节点，包括已结束的旧会话内容。
- **机制**：直接复用项目中已有的 `message_vectors` 表和 BGE-Base 向量索引，结合 `ai/tantivy_search.rs` 混合检索。哪怕是半月前的某个技术点讨论，只要当前问题高度相关，即作为 Chunk 捞回作为参考片段。

## 二、 核心痛点攻克：本地与云端双引擎自适应调度

这是确保多端切换不崩溃的核心能力。由于 **云端模型（豆包/DeepSeek）支持高并发，但本地模型（LM Studio）只有一条推理队列**，如果后台正在为了“中期摘要”疯狂占用卡槽，此时用户发消息就会被“卡死或排队”。

**系统必须实装“自适应调度”：**

### 策略 A：云端 API 激进模式 (Concurrent/Aggressive)

- **触发时机**：只要检测到当前会话消息增量累积达到阈值（如 ∆N=6）。
- **执行方式**：利用 `tokio::spawn` 瞬间抛出两个并行的后台子任务，一个请求 API 提取/更新本会话 `summary`，一个请求 API 提取 `user_profile` 增量，毫秒级响应，完全不干扰主界面的下一次聊天。

### 策略 B：本地模型惰性闲时模式 (Lazy & Idle Debounce)

- **触发时机**：引入防抖（Debounce）结合闲时检测制。用户发完消息后，启动闲时倒计时（例如 15 秒）。如果这一周期内用户未进行新的连续追问，则认为进入安全空窗期，将总结任务推入本地推理队列。
- **执行方式**：在 Rust 层建立全局的 MPSC 异步信号队列通道。
  - **ChatTask (聊天请求)**: 拥有 `Highest Priority`，具备“抢占式/中断式”权限。
  - **SummaryTask (总结请求)**: 拥有 `Low Priority`。如果闲时任务启动瞬间用户发消息，本地应当立即中断摘要推理并释放资源服务人类请求。
- **本地降级妥协**：对于本地 LM Studio，默认放弃高深度的“用户画像交叉提取（Profile）”，只保留“中期滚动摘要（Summary）”，极致压榨算力保留基础流畅度。

## 三、 SQLite Schema 数据底层轻量化演进

针对该架构，在 `vector_db.rs` 基础上不需要做破坏性重建，仅需升级表结构即可平滑过渡：

```sql
-- 1. 会话元数据表增加摘要与游标
ALTER TABLE conversations ADD COLUMN summary TEXT;
ALTER TABLE conversations ADD COLUMN last_summarized_msg_id TEXT;

-- 2. 新增全局用户画像表 (跨会话应用)
CREATE TABLE IF NOT EXISTS user_profiles (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    extracted_at TEXT NOT NULL
);
```

## 四、 对话组装流水线: The "Sandwich" Prompt 规范化

在 `commands/ai.rs` 中，现在的上下文组装较随意。必须采取更加工程验证过的“三明治”拼接结构（将各种 Context 分层锁死在固定层级，抑制幻觉）：

```text
=================== [1. 顶层指令与人设层] ===================
[System]: 你是 OneLeaf 智能知识助手。
【用户档案画像】:
- 偏好设定: 喜欢直接给代码，不需要闲聊废话。
- 业务领域: Rust Tauri 桌面端开发。

=================== [2. 中长期上下文层] ===================
【历史跨会话碎片召回】: (来自 message_vectors RAG)
- (11月2日片段): 之前讨论过 BGE-Base 向量维度需固定为 768 的问题。

【本会话早期摘要】: (来自 conversations.summary)
用户本轮前面沟通了前端页面的布局问题，确认了 Sidebar 和内容区的组件拆分。

=================== [3. 近期对话滑动窗口层] ===================
[User]: (滑动窗口第一条) 我们加个全局的消息通道怎么样？
[Assistant]: (滑动窗口回复) ...
[User]: (近期最新对话前文) ...

=================== [4. 聚焦层 (核心诉求)] ===================
[User]: (当前实际发送的提问) 那基于这个全局通道，帮我看一下刚才那段发送事件代码怎么写？
```

## 五、 落地实施 Roadmap (三步走)

建议采取稳定渐进的“小步快跑”策略进行重构整合，每一步都能在当前系统中自闭环测试工作：

### **Phase 1: 数据基建与“三明治”流水线重构 (最优先执行)**

1. 在 `vector_db.rs` 执行上述的 `ALTER TABLE` 升级与 `user_profiles` 创建。
2. 重磅重构 `commands/ai.rs` 的上下文拼合引擎（分离提取逻辑：获取 profile，获取 RAG Context，取出 Limit 的 4～6 轮 message），按“三明治规范”拼接组装送给大模型。

### **Phase 2: 后台异步精炼师 (The Summarizer) 引擎开发**

1. 建立独占业务模块 `memory_manager.rs` 来容纳闲时检测逻辑。
2. 实装策略 A 与 策略 B，利用 `tokio::mpsc` 并结合现有的 `AI_SERVICE.lock().provider_type` 做分支判断。如果为本地模式开启延迟倒计时和软中断标志位机制；利用独立的不可见系统 prompt 调用模型总结存入 `summary`。

### **Phase 3: 画像提取与 RRF 深度融通 (长期护城河)**

1. 将知识库相关的文档搜索与历史聊天记录搜索进一步在分界上融会贯通，应用 RRF (Reciprocal Rank Fusion)。
2. 开发高精度的用户特征异步提取模型，填充 `user_profiles`，让助手在多个对话间具备“前缘记忆”。

这份实施方案能够近乎完美地兼容目前 OneLeaf 成型的知识库技术基底，在不动摇其核心性能的前提下大幅拔高聊天问答的“时空记忆连贯性”。
